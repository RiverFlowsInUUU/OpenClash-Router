# 闸门与退出码协议

本仓库的**判据基础设施**。AI 改完配置后跑它，红了就修；改判据前先读本文件。

---

## 1 · 为什么要有闸门

AI 改配置的错误有两种，第二种更危险：

| 类型 | 表现 | 靠什么发现 |
|------|------|-----------|
| **明显错误** | 语法错、连不上 | AI 自己会撞上 |
| **静默错误** | 看着没问题，其实判据失效 / 凭据泄露 / 文档漂移 | **只有闸门能发现** |

本仓库是**公开**的，所以凭据泄露一旦推送就**不可回收**（要改写 git 历史）。
闸门把这类"看着全绿其实出事"的路径堵在推送之前。

---

## 2 · 退出码协议（全仓统一）

**这是跨脚本协议，不是随手返回值。** 新增或修改退出码前先读这节。

| 码 | 含义 | 使用场景 |
|----|------|---------|
| `0` | **通过** | 判据全过 |
| `1` | **判负** | 有判据不满足（含 `run` 透传的远端失败码） |
| `2` | **环境不达标** | 缺依赖、参数错、前置条件不满足。**先修环境，再看判据** |
| `3` | **SKIP（未验证）** | 必须联网/远端才能判，但网络不可达 |

### 铁律

1. **`3` 的准入 = 「没读到远端真值」**。任何脚本**不得因故障/未知错误返回 3** ——
   故障走 `2`，断言不过走 `1`。**滥用 3 会把故障吞成"跳过"，造成假绿。**
2. **`2` 与 `3` 不可复用**。若 SKIP 复用 `2`，环境故障会被读成"跳过"，聚合闸门就吞掉它 ——
   这是本项目记录在案的假绿路径。
3. **聚合闸门的口径**：任一闸门 `1` 或 `2` → 聚合返回 `1`；全部 `0` 或 `3` → `0`
   （但 `3` 必须以 `⚠️ 未验证` 明示）。**未验证 ≠ 通过。**

### 本地 vs CI 的有意差异

`check_secrets` 之类不需要网络的闸门两边一致。需要远端的（未来若加）在 CI 里
把 `3` 视为失败（CI 有 token/网络，读不到即环境异常）—— 这是**严格化**，不是"第三套判据"。

## 3 · 闸门清单

用 `python tests/verify_all.py` 一次跑完（并行，出一张汇总表）。
清单与 `.github/workflows/ci.yml` **同源** —— 改一侧必须改另一侧。

| 闸门 | 文件 | 判据 |
|------|------|------|
| **SKILL.md 合规** | `tests/check_skill_md.py` | S1-S7，见下 |
| **凭据扫描** | `tests/check_secrets.py` | C1-C3，见下 |
| **可移植性** | `tests/check_portability.py` | P1-P5，见下 |
| **oc.py 自检** | `scripts/oc.py bootstrap` | 依赖可安装、CLI 可运行 |

## 4 · 各闸门判据详解

### `check_skill_md.py`（S1-S7）

| 判据 | 内容 | 为什么 |
|------|------|--------|
| S1 | frontmatter 存在且有 `name`/`description` | Agent Skills 规范要求；缺了技能不被加载 |
| S2 | `name` 符合 `[a-z0-9]+(-[a-z0-9]+)*`，≤64 字符 | **规范硬性要求**。写成 `OpenClash-Router` 会导致某些实现拒绝加载 |
| S3 | `description` 非空，≤1024 字符 | 规范要求；这是**触发**的唯一依据 |
| S4 | SKILL.md ≤500 行 | 渐进披露原则；超了应外置到 `reference/` |
| S5 | 引用的 oc.py 子命令真实存在 | 防"文档让 AI 跑一个不存在的命令" |
| S6 | 索引的 `reference/*.md` 都存在 | 防索引漂移（SKILL.md 指向被删的文件） |
| S7 | 声称的 oc.py 行数与实际偏差 ≤50 | 防文档漂移 |

> **S2 注意**：仓库名可以是 `OpenClash-Router`（展示用），但 `name` 字段
> **必须**小写 —— 两者不同不是错误（README 有说明）。

### `check_secrets.py`（C1-C3）

**红线闸门。** 三类扫描：

| 判据 | 内容 |
|------|------|
| C1 | 禁止的文件名（`config.json`、`id_ed25519`、`.oc_creds.json`、`known_hosts`…） |
| C2 | 高置信度凭据模式（GitHub token、`sk-`、AWS key、私钥块、`AGE-SECRET-KEY-`…） |
| C3 | 本仓特有上下文（`OC_PASS=...`、`secret=...`、`OC_HOST=<真实IP>`） |

**允许的占位**（白名单，不误报）：

- `192.0.2.x` / `198.51.100.x` / `203.0.113.x`（RFC 5737 文档 IP）
- `example.com` / `*.example` / `localhost`（RFC 2606）
- `REPLACE_WITH_*` / `<你的密码>` / `xxx` / `your_*` / `TODO`

**改这个闸门很危险** —— 放松判据等于给泄露开后门。加白名单前想清楚：
这个模式真的不可能承载真实凭据吗？

### `check_portability.py`（P1-P5）

| 判据 | 内容 | 为什么 |
|------|------|--------|
| P1 | 行尾统一 LF | CRLF 会让 shell 脚本在 Linux 上炸 |
| P2 | 无 UTF-8 BOM | BOM 会被当成内容 |
| P3 | 合法 UTF-8 | 跨平台读取的基本要求 |
| P4 | Python 含非 ASCII 时有编码声明 | 否则 Windows 读取报错 |
| P5 | **print 非 ASCII 的脚本必须有 `reconfigure(encoding=...)`** | 见下 |

**P5 的由来（实测教训）**：Windows 中文环境（ACP=936）下，Python 子进程
stdout 走管道时用 cp936 编码 —— 脚本 `print` 一个非 GBK 字符（`✅`/`❌`/`⚠️`）
就 `UnicodeEncodeError` 并以**退出码 1** 结束。而 `1` 恰是本仓「判负」的码
⇒ **崩溃被读成判负**，整轮看着对、其实判据没跑。

修法：脚本开头加

```python
for _s in (sys.stdout, sys.stderr):
    try:
        _s.reconfigure(encoding="utf-8", errors="replace")
    except Exception:
        pass
```

## 5 · 改闸门时的纪律

1. **只许加固，不许放松。** 尤其是 `check_secrets` —— 本仓立身于此。
2. **改判据前先读它是否有"事故复盘"注释** —— 很多判据是踩坑后加的，
   注释里写了为什么。删掉它可能重蹈覆辙。
3. **`verify_all.py` 与 `ci.yml` 必须同步。** 改一处忘另一处 = 本地/CI 结论分歧。
   （已知挂账：机器对账未做；触发条件是"一侧增删闸门、另一侧未同步"造成实际分歧。）
4. **每条判据都要能双向验证**：故意造一个违规看它是否判负，再造一个合规看是否误报。
   —— 只能判断"绿"而不能判断"红"的闸门等于没有。
