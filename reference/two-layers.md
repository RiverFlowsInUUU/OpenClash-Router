# 两种「改」：仓库 vs 设备

**本技能最重要的概念区分。** 混淆这两层是本项目最大的事故来源。

---

## 1 · 根本差异

参考项目的形态（如配置模板仓）：**改了仓库 = 改了成品**，git 就是版本管理与回滚机制。

本技能不同：

```
┌─────────────────────────────────────────────────────┐
│  第一层：仓库（本 git 项目）                          │
│  = 工具 + 知识 + 闸门                                 │
│  改它 = 改进"怎么干活"                                │
│  闸门守它（tests/）                                   │
│  git 管它（版本/回滚）                                │
└─────────────────────────────────────────────────────┘
                        ↓ oc.py 通过 SSH
┌─────────────────────────────────────────────────────┐
│  第二层：路由器（用户的真实设备）                      │
│  = 真正要改的目标                                     │
│  改它 = 改变用户的网络行为                             │
│  ⚠️ 闸门守不到它                                      │
│  ⚠️ git 管不到它                                      │
└─────────────────────────────────────────────────────┘
```

**关键结论**：

- 闸门全绿 **≠** 路由器配置改对了。前者只证明"工具是好的"。
- `git revert` **救不了**路由器。回滚必须靠路由器上的备份。
- 用户说"改配置"，**99% 指第二层**（改他的路由器），不是改本仓库。
  改仓库只在「修工具/加知识」时才发生。

---

## 2 · 判定：这次改动落在哪一层？

| 用户的话 | 层级 | 动线 |
|---------|------|------|
| 「帮我加个节点」「改下分流」「DNS 有问题」 | **第二层（设备）** | 见 §3 |
| 「技能里补一条坑」「闸门加个判据」「优化 oc.py」 | **第一层（仓库）** | 见 §3 |
| 「把上次那个改动记下来」 | 两层都要 | 先改设备，再把经验沉淀成仓库文档 |

**只读操作（`probe` / `run "cat ..."`）不属于任何一层的"改"**，随时可做。

---

## 3 · 两条动线（不可混用）

### 动线 A · 改设备（最常见的任务）

```
① 只读侦查 → ② 拿到源文件 → ③ 本地改 → ④ 内核校验
→ ⑤ 备份 → ⑥ 替换 → ⑦ 重启 → ⑧ 设备侧验证 → ⑨ 汇报（含回滚方式）
```

**每一步的"为什么"**：

| 步 | 动作 | 为什么 |
|----|------|--------|
| ① | `probe` + 针对性侦查 | 不知道现状就改 = 赌博 |
| ② | `pull` 源文件到本地 | 路由器上没法舒服编辑，且要留原样对照 |
| ③ | 本地精确编辑 | 保留缩进/注释风格（用户以后还要看） |
| ④ | `clash -t` 在 `/tmp` 校验 | **不影响线上**就能发现语法错 |
| ⑤ | `cp -a` 备份 | git 救不了路由器，这是**唯一**回滚依据 |
| ⑥ | 替换源文件 | 改源文件，不改运行配置（§4 铁律 1） |
| ⑦ | `restart` | 让改动生效 |
| ⑧ | 查 API/日志确认 | **文件改了 ≠ 生效了**（见 §4） |
| ⑨ | 告诉用户备份路径+回滚命令 | 让他能自己退回去 |

> ⚠️ **第 ⑧ 步是 SC 那类项目没有的。** 那里"文件写对了"就等于"成了"；
> 我们这里文件写对只是前提，还必须确认**运行时真的变了**。

### 动线 B · 改仓库（修工具 / 沉淀知识）

```
① 明确要改什么、为什么 → ② 改文件 → ③ python tests/verify_all.py
→ ④ 本地 commit → ⑤ 停在推送前（push 是独立确认项）
```

**闸门只在这条动线上有意义** —— 它守的是仓库质量（凭据、编码、文档一致性）。

---

## 4 · 设备侧的特殊性（SC 那类项目没有的）

### 4.1 文件改了 ≠ 生效了

路由器是**有状态**的：运行中的核心、防火墙规则、DNS 劫持、策略组记忆、
Smart 缓存…… 改文件只改了"下次启动读的东西"。

| 改什么 | 生效方式 | 验证 |
|--------|---------|------|
| YAML 配置 | 重启核心 | 查核心 API `/proxies` |
| UCI 选项 | `uci commit` + 可能需重启 | `uci show` 确认落地 |
| 防火墙规则 | `reload`（不重启核心） | `nft list chain` |
| 覆写模块 | **必须重启核心** | `grep -c 'Overwrite Module' /tmp/openclash.log` > 0 |

**常见"改了没生效"**：改了运行配置（重启被覆盖）、覆写模块没注册（三关缺一）、
UCI 没 commit。

### 4.2 失败代价：用户全家断网

这是和 SC 类项目**风险等级的根本不同**。所以：

- **校验必须在替换之前**（④ 在 ⑥ 前），不是"改完再试"
- **备份必须在替换之前**（⑤ 在 ⑥ 前）
- **重启有断流窗口**（数秒），能热生效就别重启
- 用户可能**不在现场**（远程改配置）—— 改完自己把 SSH 也弄断了就麻烦了

### 4.3 防失联（我们独有的纪律）

改任何**可能影响远程访问**的东西之前，先想清楚"改坏了怎么救回来"：

| 风险操作 | 防失联措施 |
|---------|-----------|
| 改防火墙 / 访问控制 | 先确认还有一条不经过代理的路径（如直连 LAN） |
| 改 DNS 劫持 | 想好"DNS 挂了怎么用 IP 连回来" |
| 改 SSH / dropbear | **最后做**，且保留当前会话不断开 |
| 重启核心 | 用 `restart` 而非 `stop`（避免停在那起不来） |

### 4.4 操作不幂等

有些操作**重跑有副作用**：

| 操作 | 幂等？ | 注意 |
|------|-------|------|
| `pull` / `push` 文件 | ✅ | 随便重试 |
| `run "cat ..."` / `probe` | ✅ | 只读，安全重试 |
| `restart` | ⚠️ | 每次都断流数秒 |
| 清缓存 / 断连接 | ⚠️ | 会影响正在用的连接 |
| `kill` 进程 | ❌ | 重跑可能杀错新进程 |
| `apk del` | ❌ | 可能卡死（见 `pitfalls.md` §1） |

**重试前先想**：这个操作重跑一次会怎样？

## 5 · 哪套闸门该用在哪

| 闸门 | 守谁 | 什么时候跑 |
|------|------|-----------|
| `tests/verify_all.py` | **仓库** | 动线 B 的③（改了仓库文件后） |
| `clash -t` | **要部署的配置** | 动线 A 的④（替换前必跑） |
| 设备侧验证（查 API/日志/防火墙） | **生效结果** | 动线 A 的⑧ |
| 备份文件存在性 | **回滚能力** | 动线 A 的⑤（替换前必做） |

**记住**：`verify_all.py` 全绿只说明"工具没问题"，**不说明用户的路由器没问题**。
不要把它的绿灯当成"改设备成功了"的证据。

## 6 · 从 SC 借来的、经过转译的经验

| SC 的做法 | 原意 | 我们的转译 |
|----------|------|-----------|
| 动线 + 授权铁律 | 无命令不改文件 | **保留**，且加强：无命令不仅不改文件，**也不改设备** |
| 四态退出码 | 区分通过/判负/环境/SKIP | **保留**，全仓统一 |
| 闸门体系 | 守 profile 正确性 | **转译**：只能守仓库；设备正确性靠"校验+验证"两步 |
| `config_old/` 归档 + 升版 | 回滚机制 | **不适用**。我们的回滚是 `cp -a` 备份文件 |
| 固定名 + 版本头注 | 订阅地址稳定 | **不适用**。我们的配置文件在路由器上，不对外发布 |
| `verify_all.py` 聚合 | 一条命令跑完闸门 | **保留**，但明确它只覆盖仓库 |
| `boundaries.md` 已论定清单 | 防重复争论 | **保留** |
| 对齐断言（两内核同号） | 跨侧一致性 | **不适用**（我们没有"两侧"） |

**不照搬的判断标准**：这个机制依赖的前提，在我们这里成立吗？

---

## 7 · 一句话记住

> **闸门守仓库，校验守配置，验证守效果，备份守退路。**
> 四件事，四个不同的东西，缺一不可。
